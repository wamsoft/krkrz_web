# 起動ローディング表示とオーディオゲート

起動中にページに出すローディング表示と、ブラウザの autoplay 制限に対応する「クリックでスタート」を説明します。

## 起動ローディング表示

wasm のロード → resource の取り込み → エンジンの初期化 → **起動スクリプトの実行完了**までの間、ページの
ローディングオーバーレイを表示し続けます。以前は、エンジンの初期化以降が真っ黒で止まって見えていた区間です。
表示は段階に応じて変わります。

1. **ダウンロード中**: 「ダウンロード中 X / Y MB」+ プログレスバー (wasm 本体とデータバンドルの合計)
2. **起動スクリプトの実行中**: 起動テキスト + 「取得ファイル: N (X MB)」。prefetch (delivery:"prefetch")
   があるタイトルでは「先読み: M / 総数」とプログレスバーも出ます (prefetch はエンジンの開始後に走り始めます)
3. **完了**: (autoplay がブロックされているときだけ)「準備完了 + クリックでスタート」→ クリックですぐ開始
   します。許可されている環境では、そのままフェードアウトします

終わるタイミングは、エンジン側の**起動スクリプト完了の通知** (core の
`tTVPApplication::OnStartupScriptDone` → wasm では JS のフック `krkrzOnStartupScriptDone`) です。
デスクトップ SDL3 の splash の破棄も同じ通知にそろえています (スクリプトの完了 ≒ メインの描画の開始)。

`resource/loading.json` (タイトルの resource フォルダに置きます) で見た目を差し替えられます。

```jsonc
{
  "image": "loading.png",     // resource/ の中の背景画像 (contain で中央に表示、任意)
  "background": "#000000",    // 背景色 (任意)
  "text": "Now Loading...",   // 起動中のテキスト (任意、既定 "読み込み中...")
  "textColor": "#cccccc"      // 文字色 (任意)
}
```

`?loading=0` で以前の挙動 (wasm のロードが終わった時点で畳む) に戻せます (デバッグ用)。
スクリプトのエラー時は、エラーオーバーレイを出すと同時にローディングを閉じます。

## オーディオゲート (クリックでスタート)

ブラウザの autoplay ポリシーで音声がブロックされる環境 (AudioContext がユーザの操作まで suspended) では、
その間に鳴らした音は全て捨てられ、**起動直後のロゴの音・タイトルコールなどが欠けます**。オーディオデバイス
自体は `main()` の冒頭 (`InitAudioSystem`) で常時の無音再生込みで初期化済みなので、問題は初期化の遅れでは
なく、autoplay の制約だけです。

対策として、autoplay のブロックを起動時に probe で検知した場合だけ、**起動スクリプトの完了直後 (=
ローディング画面が消える直前、最初の発音より前)** に「クリック / タップでスタート」を差し込みます (core の
`OnStartupScriptDone` が `krkrzWaitBeforeStart()` を非同期 suspend で await します)。

- ダウンロード〜起動処理は全て通常どおり進み、**終わってから**「準備完了 + クリック / タップでスタート」に
  なります。クリックするとすぐにゲームが始まります (待ちはありません)
- それまでにページの中で一度でも操作していれば、ゲートは出ません (Web Audio の許可は sticky activation
  なので、1 回操作すれば以後有効です)
- クリックのあとで進行が再開するので、AudioContext は running の状態で、最初の音から鳴ります
- autoplay が許可されている環境 (サイトエンゲージメント / kiosk / `--autoplay-policy` の指定など) では、
  ゲートは出ません
- `?audiogate=0` で無効にできます (以前の挙動)
